# ICONIXプロセス設計書シリーズ ② ユースケース図・記述の書き方

第2回：振る舞いモデルの出発点

> 参考文献：『ユースケース駆動開発実践ガイド　オブジェクト指向分析からSpringによる実装まで』（著：ダグ・ローゼンバーグ／マット・ステファン）が提唱するICONIXプロセスの一般的な考え方に基づき作成

---

## 1. ユースケースモデルとは

ユースケースモデルは「ユースケース図」と「ユースケース記述（テキスト）」の2点セットで構成されます。ユースケース図はシステムの機能とアクター（利用者・外部システム）の関係を俯瞰する地図であり、ユースケース記述はその機能の中身（手順）を文章で詳細化したものです。ICONIXプロセスでは、この2つをセットで「振る舞いモデル（動的モデル）」の出発点として扱います。

> **位置づけ**
> ドメインモデルと同じく「①要求レビュー」で検証される成果物です。ユースケース記述の1文1文が、次の工程であるロバストネス図を作るときの直接の材料になります。

## 2. ユースケース図の書き方

- システムの外部にいる利用者・外部システムを「アクター」として棒人間で描く
- システムが提供する機能のまとまりを「ユースケース」として楕円で描く
- システムの範囲を四角形（システム境界）で囲む
- アクターとユースケースを実線でつなぐ
- あるユースケースが別のユースケースを必ず呼び出す場合は《invokes》、あるユースケースが別のユースケースより時間的に先行する場合は《precedes》の破線矢印で表す

### 2.1 記号の意味

| 記号 | 名称 | 説明 |
| --- | --- | --- |
| 棒人間 | アクター | システムの外部から利用する人・外部システム。主アクター（起点になる側）と副アクター（応答する側）に分類できる |
| 楕円 | ユースケース | アクターがシステムに対して行う、意味のあるまとまった処理単位 |
| 四角形の枠 | システム境界 | 開発対象の範囲を示す。枠の外側がアクター、内側がユースケース |
| 《invokes》破線矢印 | 呼び出し関係 | あるユースケースの実行中に、別のユースケースを必ず呼び出す（共通処理の切り出し） |
| 《precedes》破線矢印 | 先行関係 | あるユースケースが、別のユースケースより時間的に先に実行される（時系列の前後関係） |

> **採用する用語について**
> 教科書『ユースケース駆動開発実践ガイド』のICONIXプロセスでは、UMLで一般的な《include》《extend》ではなく《invokes》《precedes》の2種類のみを用いる。
>
> - 《invokes》：include相当。「必ず呼び出す」関係
> - 《precedes》：時間的な前後関係を表す関係（extendより単純で分かりやすい）
>
> 本演習でも、この2種類のみを使用し、《include》《extend》は使わないこと。

### 2.2 invokesとprecedesの違い（具体例で理解する）

この2つは混同しやすいので、「その場で結果が必要かどうか」で見分けます。

| | 《invokes》 | 《precedes》 |
| --- | --- | --- |
| 関係のイメージ | 処理の途中で他の処理を呼び出す（関数呼び出しに近い） | 先に完了していなければならない別の処理（前提条件に近い） |
| 実行のタイミング | 同じ一連の操作の中で、その場で呼び出される | まったく別のタイミング（別の日・別のセッション）で先に完了していればよい |
| 終わったらどうなるか | 呼び出した側の処理に戻り、続きが実行される | 戻らない。先行するユースケースはそこで完結する |
| 見分け方の質問 | 「今すぐこの処理の結果が必要か？」→ YES | 「これが終わっていれば、いつやったかは関係ないか？」→ YES |

#### 例①：《invokes》- 注文の途中で本人確認を呼び出す

「商品を注文する」の処理の中で、支払いに進む前に本人確認が必要になったとします。これは注文処理の"途中"で発生し、確認結果（OK/NG）がその場で必要なので《invokes》です。

```text
ユースケース名：商品を注文する
基本フロー：
 ①顧客はメニュー一覧から商品を選択する。
 ②顧客は数量とトッピングを指定する。
 ③システムは本人確認を行う。《invokes：本人確認をする》
 ④システムは在庫数を確認する。
 ⑤システムはカートに商品を追加する。
        ↓ ③の時点で呼び出される
ユースケース名：本人確認をする
基本フロー：
 ①システムはID・パスワードの入力を求める。
 ②顧客はID・パスワードを入力する。
 ③システムは認証結果を「商品を注文する」に返す。
```

ポイントは、「本人確認をする」が終わった後、必ず「商品を注文する」の③の続き（④）に戻ってくることです。まるで、注文処理の中に本人確認の処理を"埋め込んだ"ような関係になります。

#### 例②：《precedes》- 会員登録が終わっていることが前提

一方、「会員登録をする」は、注文するその場で毎回呼ばれる処理ではありません。過去のどこかのタイミングで一度完了していればよく、注文の処理の中に埋め込まれてはいません。これが《precedes》です。

```text
ユースケース名：会員登録をする
事後条件：顧客が会員として登録され、ログインできる状態になる
　　　　　（※このユースケースはここで完結し、呼び出し元には戻らない）
        ↓ 数日後、別のタイミングで…
ユースケース名：商品を注文する
事前条件：顧客の会員登録が完了している
　　　　　（＝「会員登録をする」の事後条件がすでに満たされている）
《precedes：会員登録をする → 商品を注文する》
```

「商品を注文する」の事前条件が、「会員登録をする」の事後条件と一致している点に注目してください。precedesは、このように片方の事後条件がもう片方の事前条件になっている場合によく使います。

> **まとめ**
> 迷ったら「注文の処理を止めて、今すぐこの処理を実行しないと先に進めないか？」を自問してください。YESなら《invokes》、「以前のどこかで完了していればよく、その場で実行する必要はない」ならば《precedes》です。

## 3. ユースケース記述の書き方

ユースケース図だけでは「何ができるか」の一覧にしかならないため、それぞれのユースケースについて「どういう手順で実行されるか」を文章で書き起こします。これがユースケース記述です。

### 3.1 記述項目と並び順

項目は次の順番で記述する。**事後条件は、事前条件のすぐ下（基本フローより前）に配置すること。**

| 順番 | 項目 | 内容 |
| --- | --- | --- |
| 1 | ユースケース名 | 「●●を△△する」の形式で統一して命名する |
| 2 | アクター | このユースケースを実行する主アクター／関与する副アクター |
| 3 | 事前条件（Precondition） | このユースケースが開始できるために満たされているべき状態 |
| 4 | 事後条件（Postcondition） | このユースケースが正常に完了したときに成立している状態。事前条件の直下に書く |
| 5 | 基本フロー（Basic Course） | 正常に進んだ場合の手順を、①②③…の番号付きで順番に書く |
| 6 | 代替フロー（Alternate Course） | 分岐やエラーが発生した場合の手順。①a.のように、分岐元の番号＋枝番で書く |

### 3.2 ユースケース名の命名規則（重要）

> **統一ルール**
> ユースケース名は必ず「●●を△△する」（対象語＋を＋動詞＋する）の形式で統一すること。対象が何であるかを省略しない。

| OK例 | NG例 | NGの理由 |
| --- | --- | --- |
| 商品を注文する | 注文する | 対象語（●●を）が抜けている |
| 会員登録をする | 登録 | 動詞（する）が抜けている・体言止め |
| 支払いをする | 決済 | 名詞だけで終わっている |
| 本人確認をする | Authenticate | 日本語の「●●を△△する」形式になっていない |

### 3.3 番号の書き方のルール

- 基本フローの各ステップには①②③…の丸数字を使う（半角数字＋ピリオドは使わない）
- 代替フローは、分岐元の丸数字＋アルファベットの枝番で書く（例：③から分岐する代替フローは「③a.」）
- 同じステップから複数の代替パターンがある場合は「③a.」「③b.」のように枝番を増やす
- 1文＝1アクション（1つの文に複数の動作を詰め込まない）
- 「アクターが〜する」「システムが〜する」のように、動作の主体を明確にする
- 画面のレイアウトやUIの詳細（ボタンの色、配置など）は書かない
- 実装技術（GET/POSTなど）に踏み込みすぎない。ユースケース記述はあくまで業務的な振る舞いを書く段階

### 3.4 記述例

```text
ユースケース名：商品を注文する
主アクター：顧客
事前条件：顧客がメニュー一覧を閲覧できる状態である
事後条件：選択した商品がカートに追加された状態になる
基本フロー：
 ①顧客はメニュー一覧から商品を選択する。
 ②顧客は数量とトッピングを指定する。
 ③システムは在庫数を確認する。
 ④システムはカートに商品を追加する。
 ⑤システムはカートの内容と合計金額を表示する。
代替フロー：
 ③a. 在庫が不足している場合、システムはエラーメッセージを表示し、
      在庫のある商品のみを表示する。
```

> **ポイント**
> 基本フローの1文1文（「顧客が選択する」「システムが確認する」「システムが追加する」…）は、そのまま次のロバストネス図における一連のメッセージ（矢印）の元ネタになります。文を分けて書くほど、ロバストネス図に変換しやすくなります。

## 4. よくある間違い

- 1つの文に複数の処理を詰め込んでしまう（例：「商品を選び、数量を入力し、カートに入れる」を1文で済ませる）
- 画面の見た目（UI）の説明に終始してしまい、システムの振る舞いが書かれていない
- 事前条件・事後条件を省略してしまう → ロバストネス図やテストケースの起点が失われる
- 事後条件を基本フローの最後にだけ書いてしまう → 事前条件の直下（基本フローより前）に配置する
- 基本フローに例外処理を混ぜてしまう → 例外・分岐は必ず代替フローに分離する
- ユースケース名が「●●を△△する」の形式に統一されていない（対象語や動詞の欠落、体言止めなど）
- 《include》《extend》を使ってしまう → 教科書の方式に合わせ《invokes》《precedes》のみを使う

- [ ] 基本フローが①②③…の丸数字で書かれているか
